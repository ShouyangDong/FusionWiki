# FusionWiki entry schema

Every file under `entries/` contains one JSON object per line (JSONL). Each
line is one **measured** outcome, written by MASTER at the moment a
candidate is evaluated or admitted.

## Entry fields

| Field                       | Type      | Meaning                                                      |
| --------------------------- | --------- | ------------------------------------------------------------ |
| `lesson_key`                | `str`     | Namespaced semantic bucket; see below.                       |
| `domain`                    | `str`     | Experience domain: `fusion_boundary` or `plan_mutation`.     |
| `pattern`                   | `str`     | Descriptive label, e.g. `ProviderVariantMutationOperator/` + mutation kind, or a fusion pattern name. |
| `op_sequence`               | `[str]`   | Canonical op targets in region order, oldest producer first.  |
| `kind_sequence`             | `[str]`   | Per-node kinds: fx op kind for `plan_mutation`, semantic kind (e.g. `elementwise`) for `fusion_boundary`. |
| `dtypes`                    | `[str]`   | Sorted unique dtypes in the region.                          |
| `strategy`                  | `str`     | What was tried: `"<provider>:<variant>"` for plan mutations, a free-text strategy for fusion boundaries. |
| `phase`                     | `str`     | Search phase, e.g. `exploration` or `final_admission`.       |
| `status`                    | `str`     | Measurement outcome, e.g. `accepted`, `rejected`, `measured`, `failed`. |
| `accepted`                  | `bool`    | Whether the candidate passed admission in this round.        |
| `improvement_vs_parent_pct` | `float?`  | Marginal effect versus the parent plan/boundary (child-vs-parent score delta). The transferable signal. |
| `improvement_pct`           | `float?`  | Whole-candidate improvement versus the compiled baseline.    |
| `environment`               | `{str: any}` | Runtime fingerprint (torch version, device, backend, ...). Entries under a different environment than the reader's are excluded from all derived knowledge. |
| `timestamp`                 | `float`   | Unix time; also selects the `<yyyy-mm>` shard directory.     |

Model-specific facts (node names, binding ids, concrete shapes) are
deliberately **not** stored — the same archetype on a different model must
map to the same lesson bucket.

## Lesson key

```text
lesson_key = sha256({
    kinds:     kind_sequence,          # ordered
    dtypes:    sorted(unique dtypes),
    ranks:     sorted(unique ranks),   # rank = len(shape) per node
    environment,
})
```

The `fusion_boundary` domain uses this bare digest, exactly as recorded by
every wiki written before domains existed. Every other domain prefixes it:

```text
plan_mutation lesson_key = "plan_mutation:" + sha256({...})
```

## Domains

- **`fusion_boundary`** — measured outcomes of candidate fusion boundaries,
  written during LLM-guided fusion evolution. Feeds warm-start boundary
  injection: historically winning op sequences seed the next model's
  evolution population.
- **`plan_mutation`** — measured outcomes of execution-plan mutations
  (provider/variant assignment on a region archetype), written by the
  execution-plan search. The region's semantic signature plus the
  `provider:variant` strategy records which lowering choice tends to win for
  which kind of subgraph on which environment.

## Derived views

`lessons/` holds aggregates regenerated by `tools/rebuild.py` from `entries/`:

- `lessons/<lesson_key>.json` — per-bucket statistics: grouped by
  `op_sequence :: strategy`, with observation counts, accepted/rejected
  counts, and median/MAD of improvement.
- `winning_boundaries/<lesson_key>.json` — top-ranked op sequences
  (accepted at least once, or positive median improvement), used for
  warm-start injection.

The derivation logic lives in MASTER
(`master.planning.fusion_wiki`); `tools/rebuild.py` is a thin wrapper so
this repository never carries a second implementation.
